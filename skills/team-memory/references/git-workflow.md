# Публикация и конкуренция

## Начало запроса

Для чтения ветка не нужна. Для изменения использовать отдельную рабочую копию или
worktree и ветку запроса. Сначала `git status --short`, `git remote -v` и проверка
доступности origin. Не переносить чужие незакоммиченные изменения. Базовую ветку
определять по remote HEAD/настройкам репозитория, не угадывать `main`.

Получить origin, записать исходный SHA основной ветки. Пример для подтверждённой `main`:

```sh
git fetch origin
git rev-parse origin/main
git worktree add -b memory/daily-2026-10-19 ../memory-daily-2026-10-19 origin/main
```

Если платформа предоставляет управляемые worktree, пользоваться её инструментом.
Имена веток и каталогов уникальны для запроса. При отсутствии remote сохранить локальную
ветку, проверить файлы и сообщить, что публикация недоступна; не заявлять общий результат.
В новой пустой базе допустим локальный bootstrap-коммит без данных; содержательные
изменения всё равно готовятся в рабочей ветке для первого PR.

## Смысловая сверка

После обработки источников и локальных проверок зафиксировать изменения рабочей ветки,
ещё раз получить origin. Сравнить первоначальный SHA с актуальным base SHA.
Одна попытка — fetch → интеграция при необходимости → смысловая сверка → проверка
структуры → повторный fetch и сравнение SHA. Не более трёх таких попыток за обращение.

При сдвиге base прочитать изменения между исходной и текущей основной веткой и намерение
своего запроса. Использовать обычный merge основной ветки в рабочую; не переписывать чужую
историю. Успех Git merge не означает смысловую совместимость.

- Сохранить совместимые независимые изменения, даже в одном файле.
- Повторить поиск по проекту, системе, теме и ожидаемому результату во всей базе,
  включая новые файлы другой ветки и закрытые задачи.
- При одинаковом новом знании использовать ID первой опубликованной записи, перенести
  свои дополнения и исправить неопубликованные ссылки; убрать только свой неопубликованный
  дубль. Не создавать redirect для ID, который ещё не был опубликован.
- При конфликте ответственных, закрытия и нового блокера или смысла знания не выбирать
  молча последнюю версию. Сохранить обе версии и их источники в рабочей ветке. Для
  текстового конфликта использовать явные секции с вариантами, а не маркеры Git, чтобы
  не потерять изменения. В PR описать необходимое решение человека.
- После интеграции выполнить валидатор и нужные тесты. Если база снова сдвинулась —
  следующая попытка. После трёх неудач сохранить ветку, исходный и последний SHA,
  диагностировать препятствие и остановить текущую сверку. Следующий запрос может продолжить.

## PR и merge

Публиковать только рабочую ветку обычным push и открыть PR. Нельзя делать прямой или
принудительный push основной ветки, выполнять merge PR или включать auto-merge.
Если остался смысловой конфликт или исчерпаны попытки, возможен только draft PR.
Если push/создание PR недоступны, сохранить ветку и точное описание оставшегося шага.

Использовать `.github/pull_request_template.md`: источники; что создано/обновлено;
повторы; вопросы; проверки; первоначальный и последний сверенный SHA основной ветки.
После push ещё раз проверить base. Если он изменился, PR нельзя объявлять готовым до
новой сверки в пределах оставшихся попыток. Успешный push чужой рабочей ветки не вызывает
конфликт сам по себе: конкуренция проявляется при сдвиге общей основной ветки.

Перед merge человек сверяет записанный SHA с текущим base. Если они различаются,
запрашивает у агента повторную сверку; агент обновляет ветку, проверку и описание PR.
Зелёный CI проверяет структуру, но не подтверждает смысловую сверку. Проверять непосредственно
перед merge, а не только при первоначальном ревью. Настройка защиты — [setup](../../../docs/github-setup.md).

## Отчёт

Различать четыре состояния: сохранено локально; ветка отправлена; PR открыт;
PR фактически merged человеком (проверить, прежде чем утверждать). Первые три означают
«предложено». Сообщить ветку/PR, проверенный base SHA, выполненные проверки и открытые вопросы.
Отказ публикации не уничтожает подготовленные изменения. Не отправлять сообщений коллегам
или в чат команды без отдельного запроса.
