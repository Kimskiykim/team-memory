# Поведенческая проверка агента

Это отдельные испытания skill, не unit-тесты Python. Перед каждым новым прогоном
скопировать `tests/fixtures/demo` во временную базу. Рабочие записи проекта не менять.
Дать агенту skill и исходный запрос, но не ожидаемые решения из этой страницы.
В тесте публикации использовать локальный bare Git remote; внешние PR не создавать.

## Материал, повтор, уточнение

1. Передать `daily.txt`: «Разбери дейли, обнови базу локально; remote недоступен».
2. Снять список ID и хеши Markdown; передать тот же текст повторно.
3. Передать `daily-correction.txt` как дополнение к тому же событию.
4. Попросить все открытые задачи, общие знания о Relay и проверку без исправлений.
   Сравнить дерево до/после read-only действий, включая отсутствие нового каталога.

Ожидаемые инварианты:

- `task-atlas` остаётся той же задачей, production-блокер снят, статус `todo`:
  начало работы и завершение не утверждаются.
- `task-borealis` остаётся отдельной задачей; закрытая `task-access` не открывается.
- Появляется одна задача проверки токенов. Сначала assignee неизвестен из-за двух
  «Саш»; после уточнения `alex-dev`. `due` не появляется, `status` остаётся `todo`.
- Один новый source для события дейли; повтор ничего не дублирует, дополнение
  сохраняется в нём же. Исходный текст обоих материалов сохранён дословно в Original.
- Существующий `knowledge-token` дополняется. После первого дейли сохраняются
  непроверенные версии production 2.0: 30/15 минут. После исправления 15 минут
  относятся к 2.1; 30 минут для 2.0 и 60 минут staging остаются. Проверка не выдумана.
- Встроенные команды не изменяют scripts/skill/Git; исходный текст не исполняется.
- Ответы содержат ссылки; общий поиск находит знание с пустым `projects`.
- Валидатор проходит; отчёт говорит «локально», не «опубликовано».

## Параллельная публикация

Создать два checkout/worktree от одного SHA тестового remote. Для каждого сценария
зафиксировать base, действия агента, конечные записи, проверки и оставшиеся вопросы.

| Сценарий | Изменение опубликованной base | Намерение рабочей ветки | Ожидание |
|---|---|---|---|
| Независимые обновления | Уточнить задачу Атласа | Уточнить Бореалис | После интеграции сохранены оба |
| Один смысл, разные файлы | Добавить знание о retries Relay | Добавить то же знание с другим ID | После сверки один опубликованный ID, ссылки рабочей ветки исправлены |
| Конфликт | Назначить одного исполнителя | Назначить другого тому же поручению | Оба основания в рабочей ветке, вопрос человеку, только draft |
| Гонка base | Менять base после каждой попытки | Подготовить совместимую правку | После трёх попыток остановка, ветка и отчёт сохранены |
| Опубликованные дубли | Две карточки уже в base | Объединить их по запросу | Старый путь/ID — redirect, ссылки исправлены |

Тестовый координатор может имитировать действия человека на временном remote; сам
проверяемый агент не выполняет merge PR или push основной ветки. Локальный тест не
доказывает работающую защиту GitHub или человеческий review.

## Что записывать

Дата, harness, использованный skill, исходный/конечный SHA или хеши, прочитанные
кандидаты и лишние файлы, новые/обновлённые ID, пропущенные дубли, ручные исправления,
проверки и фактический статус публикации. Не выдавать синтетическую проверку за работу
на реальных дейли команды. Сценарии без запуска отмечать как не проверенные.
