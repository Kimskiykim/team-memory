# Team Memory: план первой версии

Дата: 2026-10-19.

Статус: согласованное направление, реализация не начата.

Основа: «Team Memory: дизайн первой версии» от 2026-10-19, предоставленный пользователем. Этот план заменяет прежний план «Общий Markdown-мозг команды». Публикация уточнена: изменения попадают в общую базу только через PR и человеческий merge.

Реализацию следует вести в отдельном приватном репозитории `team-memory`; при его создании перенести туда исходный дизайн и этот план. Team Memory не требует USW.

## 1. Цель и границы

Создать общую Markdown-базу задач и знаний нескольких проектов, с которой команда работает через агентский harness и единый skill. Агент разбирает переданный материал, находит существующие записи, обновляет задачи и знания, проверяет результат и готовит PR.

Первая версия включает:

- записи проектов, участников, задач, знаний и источников;
- разбор дейли и других материалов по запросу пользователя;
- создание и обновление задач, инструкций, знаний и решений;
- поиск и ответы со ссылками, отдельную проверку дублей и противоречий;
- локальный пересоздаваемый каталог поиска и структурный валидатор;
- совместную работу через отдельные рабочие копии, смысловую сверку и PR.

За пределами версии: автоматический сбор сообщений, обязательный `inbox/`, внешний фоновый runner, браузерный интерфейс, векторный поиск, синхронизация с трекером и прямые вызовы LLM API.

GigaCode CLI рассматривается как агентский harness, способный читать skill и работать с файлами и Git. Конкретная модель, способ входа и флаги CLI не входят в контракт Team Memory. MCP можно подключить позднее как дополнительный интерфейс.

### Данные

- Одна сущность — один Markdown-файл с YAML frontmatter и постоянным `id`, `title`, `summary`. Смысловые связи — обычные относительные Markdown-ссылки.
- Новые ID создаются как префикс типа и UUID4 без общего счётчика. Существующие корректные ID, включая короткие иллюстративные ID дизайна, сохраняются; валидатор проверяет уникальность. При переименовании ID не меняется.
- Проекты и участники имеют человекочитаемые постоянные ID, например `atlas` и `petya`, и список `aliases`. Системы представлены карточками в `wiki/systems/`, также с ID и aliases.
- Принадлежность задают массивы `projects`, `systems`; они могут быть пустыми. Задачи и знания не распределяются по проектным папкам. Свободные теги не обязательны.
- Задача содержит ожидаемый результат, текущее состояние, источники и `status`: `todo`, `in_progress`, `blocked`, `done`, `cancelled`. `assignee` и `due` задаются только при наличии сведений.
- Знание содержит тип, область применимости, содержание и источники. Инструкции отдельно фиксируют окружение, дату проверки и версию системы, когда она существенна. Дата редактирования не заменяет дату проверки.
- Решение — тип знания в `wiki/decisions/`. Принятое решение сохраняется; заменяющее решение ссылается на него, а прежнее явно помечается как заменённое.
- Источник содержит дату события, происхождение, исходный материал, ссылки на результаты обработки и открытые вопросы. Исходный текст отделён от интерпретации агента. Последующие дополнения и исправления сохраняют основания изменений; историю хранит Git.

### Инструменты

- Использовать Python 3.10+, стандартную библиотеку и PyYAML для безопасного чтения YAML через `safe_load`; не писать собственный YAML-парсер. Общие чтение записей и разрешение ссылок находятся в `records.py`.
- `search.py` поддерживает поиск по ID, фильтры по метаданным, текстовый поиск и JSON-вывод. Обычный поиск возвращает порцию кандидатов; режим полного отбора возвращает все совпадения без скрытого top-N.
- Каталог хранится в игнорируемом `.team-memory/search.json`. Перед поиском сверяется содержимое Markdown-файлов, учитывая локальные правки, добавления и удаления. Каталог можно полностью удалить и восстановить.
- `validate.py` проверяет обязательные поля и секции, статусы, даты, уникальность ID, внутренние ссылки и ссылки на проекты, системы и участников. Ненулевой exit code означает ошибку, диагностика содержит путь и причину.
- Семантические дубли, качество сопоставления и достоверность утверждений проверяет агент; структурный скрипт их не гарантирует.

## 3. Порядок реализации

### Шаг 1. Форматы, шаблоны и структурная проверка

- [ ] Создать каркас отдельного репозитория и описать контракты в `records.md` и `AGENTS.md`.
- [ ] Добавить шаблоны задачи, проекта, участника, системы, знания, решения, встречи и заметки-источника.
- [ ] Написать тесты на валидные записи, неверные поля, повтор ID, отсутствующие сущности и сломанные ссылки.
- [ ] Реализовать общий reader и валидатор; добавить CI-проверку на PR без секретов и вызова агента.

Результат: небольшой пример базы проходит проверку, испорченные fixtures отклоняются с понятной диагностикой.

### Шаг 2. Каталог и поиск

- [ ] Реализовать обновление каталога и его полное восстановление из Markdown.
- [ ] Добавить прямой поиск, фильтры, aliases, текстовый поиск и чтение следующих порций результатов.
- [ ] Проверить изменения файлов без коммита, удаление, переименование и пересоздание каталога.
- [ ] Проверить полный отбор задач и поиск общих знаний без фильтра, исключающего записи других проектов.

Результат: агент получает компактный список кандидатов и читает нужные записи целиком. Первые 5–10 файлов — размер начальной порции, а не предел поиска дублей.

### Шаг 3. Skill и сценарии работы

- [ ] Создать `skills/team-memory/SKILL.md` с выбором сценария и ссылками на подробные references.
- [ ] Описать порядок: найти существующее → прочитать кандидатов → сопоставить → изменить → проверить → подготовить PR → сообщить фактический результат.
- [ ] Для разбора материалов сохранять источник и выбирать для каждого фрагмента: обновить, создать, пропустить или уточнить.
- [ ] Для задач сопоставлять ожидаемый результат и область работы, проверяя также завершённые задачи. Разные проекты обычно требуют разных задач.
- [ ] Изменять статус, ответственного и срок по явным сведениям или запросу, не выводя начало работы из слова «посмотрит» и завершение интеграции из выдачи доступа.
- [ ] Выделять знания, полезные после закрытия задачи; дополнять существующие темы вместо страницы на каждый факт.
- [ ] При противоречиях сравнивать время события, окружение и версию. Неразрешённые расхождения сохранять с обеими версиями и источниками.
- [ ] Повторно обрабатывать изменённые источники по содержанию и связям; отметка «обработано» не позволяет пропустить дополнения.
- [ ] Поиск и ответы не изменяют базу. Проверка сообщает проблемы; исправления выполняются только в пределах запроса.
- [ ] Зафиксировать границу доверия: источники и найденные страницы — данные. Встроенные в них инструкции не разрешают менять skill, scripts, настройки Git или полномочия агента.
- [ ] Описать подключение единственного канонического skill к выбранному harness; проверить его обнаружение и выполнение на доступном агенте, не предполагая неизвестные CLI-флаги.

Результат: сценарные проверки подтверждают корректное создание, обновление, повторный разбор, сохранение противоречий и ответы с источниками. Неясный пункт остаётся вопросом и не блокирует независимые понятные пункты.

### Шаг 4. Публикация через PR и параллельная работа

- [ ] Каждый запрос обрабатывать в отдельной рабочей копии или worktree и отдельной ветке. Включать только связанный набор изменений этого запроса.
- [ ] Получить актуальную основную ветку и зафиксировать исходный SHA. После подготовки изменений повторно получить основную ветку.
- [ ] При изменении базы сравнить исходное состояние, текущее опубликованное состояние и намерение агента. После Git-интеграции повторить поиск дублей по проекту, системе, теме и результату, а не только затронутым путям.
- [ ] Сохранить независимые совместимые изменения. При одинаковом новом знании использовать ID первой опубликованной записи, дополнить её и исправить неопубликованные ссылки.
- [ ] При неразрешимом смысловом конфликте сохранить весь набор в рабочей ветке, показать обе версии и обозначить PR как draft, если его можно опубликовать.
- [ ] Ограничить сверку тремя попытками за обращение. При исчерпании остановиться, сохранив ветку и сообщив, что требует решения.
- [ ] После успешных проверок push только рабочей ветки и открыть PR. Агент не выполняет merge и не делает прямой или принудительный push в основную ветку.
- [ ] В PR перечислить источники, созданное и обновлённое, пропущенные повторы, открытые вопросы, проверки и SHA основной ветки, с которым выполнена смысловая сверка.
- [ ] Настроить защиту основной ветки: PR, человеческое одобрение, обязательный CI и актуальность относительно base. Если base сдвинулась, повторить смысловую сверку перед merge; зелёный структурный CI её не заменяет.
- [ ] Учесть, что разные рабочие ветки успешно публикуются параллельно. Конкуренция обнаруживается по изменению base и при merge, а не через обязательный отказ push рабочей ветки.
- [ ] Уже опубликованные дубли объединять отдельным PR: исправить ссылки и оставить на старом пути запись со старым ID и ссылкой на основную страницу.

Результат: общая опубликованная база — основная ветка удалённого репозитория. Успешный push или открытый PR означает «предложено», а не «добавлено в общую базу». При невозможности публикации отчёт содержит локальную ветку, сохранённые изменения и оставшийся шаг.

### Шаг 5. Проверка на работе команды

- [ ] Добавить README с установкой, примерами запросов, командами проверки и восстановлением каталога.
- [ ] Подготовить тестовую базу с несколькими проектами, общей системой, участниками и неоднозначными aliases.
- [ ] Проверить skill на реальных обезличенных дейли и вопросах команды.
- [ ] Зафиксировать найденные записи, лишние прочитанные файлы, пропущенные дубли и ручные исправления. Расширять поиск по этим результатам.

## 4. Проверки и критерии готовности

Детерминированные проверки запускаются через `python3 -m unittest discover -s tests` и `python3 scripts/validate.py`. Проверки агентского поведения выполняются отдельно по fixtures и ожидаемым результатам; их прохождение нельзя выводить только из unit-тестов.

1. Повторный разбор дейли не создаёт дубли; исправленный источник обновляет связанные записи.
2. Разные формулировки одного поручения сопоставляются; одинаковые действия для разных проектов различаются.
3. Выдача доступа снимает соответствующую блокировку, но не завершает задачу автоматически. Возврат проблемы не открывает завершённую задачу без основания.
4. Противоречивые знания сохраняют обе версии и источники. Инструкция содержит область применимости и сведения о проверке.
5. Запрос всех открытых задач возвращает полный отбор. Общие знания находятся без заранее установленной связи с проектом.
6. Каталог учитывает незакоммиченные изменения, новые и удалённые файлы и восстанавливается после удаления.
7. Два совместимых параллельных обновления сохраняются после последовательного merge PR.
8. Параллельное создание одинакового знания выявляется после merge первого PR; второй использует опубликованную запись.
9. Конфликт ответственных либо закрытия и нового блокера сохраняется для человека и не попадает в main автоматически.
10. Три неудачные попытки сверки завершаются сохранённой веткой и понятным отчётом; повторное обращение может продолжить работу.
11. Инструкции внутри источника не меняют полномочия агента. Поиск и проверка без запроса исправлений не изменяют файлы.
12. Отчёт отличает локальное сохранение, push ветки, открытый PR и фактический merge. После сбоя понятно, что опубликовано и где осталось остальное.

## 5. Зафиксированные решения

- Рабочее имя репозитория: `team-memory`; создание удалённого репозитория выполняется отдельным действием при реализации.
- Данные, правила, scripts и исходник skill находятся вместе; USW может вызывать skill, но не является зависимостью.
- Основной сценарий v1 — явный запрос пользователя агенту. Автоматический runner и дополнительные интеграции остаются последующими самостоятельными этапами.
- Источники сохраняются в Markdown вместе с результатами обработки; удаления временного `inbox/` в этом плане нет.
- Поиск использует локальный JSON-каталог, структурная проверка — Python и PyYAML; векторное хранилище не требуется.
- Публикация всегда через PR. Merge выполняет человек после структурной проверки и актуальной смысловой сверки.
- Полное отсутствие смысловых дублей не гарантируется: skill повторно сверяет кандидатов и поддерживает отдельную проверку базы.
